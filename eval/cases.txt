# 若息「脑」的 tool-calling 评测集。
#
# 格式(用 | 分三列):
#     用户指令 | 期望的工具(`/` 分隔多个可接受,写 `-` = 不该调任何工具) | 参数里必须出现的子串(留空 = 不检查)
#
# ⚠️ 第三列是**字面子串**比对,`/` 只在第二列有意义。往第三列写 `a/b` 会变成
#    「参数里得出现字符串 a/b」这种永远满足不了的条件 —— 踩过一次(别放音乐了)。
#
# 怎么用:改完 AiAgent.kt 里的 SYSTEM_PROMPT / TOOL_SCHEMA 之后跑一遍 run_eval.py,
# 只看「命中率」和「打偏了哪些」,别凭手感判断改好没改好。
#
# 写用例的原则:
#   - 把 SYSTEM_PROMPT 里那 5 条 few-shot 原样抄进来当基线(它们必须过,不过说明提示词被改坏了);
#   - 其余尽量用**没在提示词里出现过**的说法(换动词、换语序、带点口语),
#     否则测的只是「模型会不会背例子」。
#   - 模棱两可的(「停一下音乐」既像暂停又像停止)两种都算过,别把合理答案判成错。

# ---- 通用入口:手机自己身上的事(2026-10-04,S3) ----
#
# 这一组盯的是新加的那条阶梯。两个方向都要钉:
#
#   ① **「手机上的事」不许调成电脑的工具**。最毒的是「打开微信」——
#      电脑那只手上也有 open_app,调它会**真的开一个电脑上的微信**,
#      不报任何错,用户看到的是「她在另一台机器上忙活」。这类错静默。
#   ② **电脑上的事不许被这条阶梯传染**。加了 list_hands 之后,
#      要是连「打开记事本」都先绕一圈菜单,那每一件电脑上的事都白多一轮。
#
# ★ 两列都写 list_hands/use_hand:阶梯本来就是两轮的(先看菜单,再动手),
#   而评测只发一轮。先调 list_hands 是完全正确的第一步,别把它判成错。
# ★ **第三列一律留空**(2026-10-04 真机实测改的)。第三列是**子串比对**,而工具名
#   只有第二轮(use_hand)的参数里才可能出现 —— 第一轮 list_hands 的参数是空的,
#   于是这几条**从设计上就不可能过**。我先前真把工具名填上了,跑出来
#   「命中 2/10 = 20%」:八条打偏有七条是**量具坏了**,不是她做错了。
#   第二轮怎么验:**不靠这个量具,靠真机端到端** —— 「设一个 7 点的闹钟」,看系统闹钟
#   真起来没有,那才是判据。离线比对在这里只会更脆:use_hand 的 args 是一层嵌套
#   JSON 字符串,再叠一层转义,拿任何参数值做子串比对都是在赌。
#   第二轮各自该出现的工具(真机验的时候对着看):
#     六点半闹钟→set_alarm  手机相机→open_phone_app  天气→web_search
#     bing 网址→open_url    剪贴板→copy            震动→vibrate     10086→dial
# ⚠️ 提示词里那两条例子(7 点闹钟 / 手机上开微信)不要抄进来 —— 那测的是背书。
